Bなぜこのプロジェクトを作ったのか

直接は知り合いではない人同士でも、驚くほど少ない仲介者を介してつながっているという「スモールワールド」的な考え方に以前から興味がありました。この抽象的なアイデアを、実際にクエリを投げて、可視化して、自分で触って確かめられる何かに変えてみたいと思ったのが出発点です。

概念だけのデモを作って終わりにするのではなく、実際のWikipediaデータ、グラフ探索アルゴリズム、フロントエンドのグラフ可視化、そして再現可能なデータパイプラインを備えた、本物のWebアプリケーションとして作ることにしました。

正直に書いておくと、「Six Degrees(6次の隔たり)」は社会ネットワーク論・スモールワールド研究に由来する概念であり、「任意の2人が必ず6ステップ以内でつながる」という保証ではありません。本アプリは、その考え方を土台にしたインタラクティブなグラフ探索アプリケーションです。実際の最短経路は0ステップ(同一人物)から、データセット中に経路が存在しない場合(found: false)まで、入力次第で変わります。

CSix Degrees of Separation とは

人物は社会グラフ上のノードとして表現でき、人間関係はそのノード間のエッジとして表現できます。2人の人物の間の「距離」は、その2人をつなぐ仲介関係の数として表現できます。

「6次の隔たり」というアイデアは、スモールワールド現象に関する研究、特にスタンレー・ミルグラムのよく知られたスモールワールド実験に由来します。一般に広まっている解釈は、社会ネットワークは驚くほど短い連鎖を通じて、遠く離れた個人同士をもつなげてしまう、というものです。

本プロジェクトは、このアイデアをインタラクティブなグラフ探索アプリケーションの発想の土台として使っています。ここは明確に区別しておきたい点です。

区分内容
理論・社会科学上の概念スモールワールド現象、ミルグラムの実験、「6次の隔たり」という通俗的な言い回し ── これらは本プロジェクトが検証・証明するものではありません。
このプロジェクトで実装した graph searchWikipedia記事間のリンクを有向エッジとしたグラフ上で、BFS(幅優先探索)により2人物間の最短経路を実際に計算するプログラムです。

DこのWebアプリで何をしているか

実際の処理フローは以下の通りです。

人物A → 人物B(英語 / 日本語のどちらでも入力可。PersonComboboxがクライアント側で入力補完)
↓ GET /api/search
Resolver(英語・日本語のエイリアスを canonical name に解決)
正規表記が完全一致すれば最優先。曖昧な場合は候補を全件返す(推測しない)。
↓
BFS(隣接リスト上の幅優先探索、enqueue時にゴール判定)
↓
shortest path + levels(探索の各段階で発見されたノード一覧)
↓ 1回のHTTPレスポンスに全て含む
GraphView(3d-force-graph / Three.js による3Dグラフ描画)
レベルを一段ずつ、一定間隔でアニメーション表示。追加のAPI呼び出しやBFSは行わない。

英語 / 日本語 / エイリアス解決

入力された名前は、正規化(NFC・全角スペース処理など)の後、canonical name(英語版Wikipediaの正式タイトル)に解決されます。英語のリダイレクト、日本語のタイトル、日本語のリダイレクトが、すべて同一人物の canonical name に対応付けられています。このエイリアス解決はオフラインのFetcherが事前に計算したものであり、実行時にWikipediaへ問い合わせることは一切ありません。

canonical name と曖昧解決

完全一致する canonical name が最優先されます。入力の正規化後の形が複数の候補に一致する場合は「曖昧」と判定され、レスポンスには該当する候補がすべて、ソートされた状態で含まれます。どれか一つを推測で選ぶことはありません。

BFS 最短経路

backend/app/graph.py の shortest_path() が、事前計算済みの有向グラフ(隣接リスト)上で幅優先探索を行います。ゴール判定を dequeue 時ではなく enqueue 時に行うことで、目的の人物が見つかった瞬間に探索を打ち切ります。

levels と経路の可視化

APIレスポンスには、最短経路そのものに加えて、BFSの各深さ(レベル)で発見されたノードの一覧(levels)が含まれます。フロントエンドはこのlevelsとpathだけを使ってグラフを描画します ── 独自にBFSを再実行することも、新たなAPIを呼ぶこともありません。

PersonCombobox(入力補完)と Search Log パネル

PersonComboboxは、起動時に一度だけ GET /api/people を呼び出し、以降はブラウザ内で完全にフィルタするクライアント専用のオートコンプリートです。新しいバックエンドのエンドポイントは追加していません。Search Log パネルは画面上「Connected」/「Disconnected」と表示されますが、実際にサーバーへ常時接続しているわけではありません ── すでに取得済みのSearchResponseを、グラフと同じレベル単位のタイマーでクライアント側だけで再生しているものです。

share URL と OG メタデータ

/share?p=A&p=B&... は、渡された経路をサーバー側で 再検証し(validate_path、GET /api/path と共通の関数)、有効な場合は Open Graph タグ(og:title、og:image、og:url)をHTMLに注入して返します。これにより、JavaScriptを実行しないチャットアプリのクローラでもプレビューが正しく表示されます。og:urlのスキーム(http/https)はリクエストの実際のベースURLから組み立てられ、リバースプロキシ配下では FORWARDED_ALLOW_IPS で信頼するプロキシを明示することで正しいHTTPSが反映されます。

検索履歴

検索履歴は localStorage に最大20件、ブラウザ単位で保存されます。アカウントやサーバー側の保存は一切ありません。

Docker ランタイム

本番相当の実行環境は、フロントエンドのビルド成果物とバックエンド(FastAPI)、そして公式データセット(3つのJSONファイル)を1つのコンテナイメージに焼き込んだものです。実行時に外部ネットワークへ出る通信は一切なく、唯一の例外はブラウザが人物のサムネイル画像をWikimediaの画像CDNから直接読み込む通信です。

GTechnical highlights

実際に実装済みの技術的判断のうち、特に説明価値が高いものを挙げます。

1. BFS shortest-path search
隣接リスト上の幅優先探索。ゴール判定を enqueue 時に行うことで、目的の人物が見つかった瞬間に打ち切る。決定性は「探索順序を特別扱いする」のではなく「探索前にデータをソート済みにしておく」ことで担保。
2. 多言語対応リゾルバー / エイリアスシステム
英語canonical、英語リダイレクト、日本語タイトル、日本語リダイレクトを同一人物に解決。曖昧な入力は候補を全件返す(推測しない)。Unicode正規化(NFC、全角スペースなど)を明示的な1行の式としてSPECに固定。
3. オフラインデータセットパイプライン
Fetcher(backend/fetcher.py)がMediaWiki Action APIから手動実行でデータを取得。実行間隔はWikimediaのRobot policyとレート制限ページを実際に確認した上で0.32秒に設定。
4. トランザクショナルなデータセット差し替え
3つの出力ファイルをセットで検証してからステージングに書き込み、全チェックを通過した場合のみ data/ を差し替える。検証失敗時は既存データセットがそのまま残る。
5. 実行時に外部ネットワーク依存がないランタイム
データセットはDockerビルド時にイメージへ焼き込み、実行時はRAM上のデータのみを参照。httpxすらランタイムイメージにインストールされていない。
6. 3Dグラフビュー(3d-force-graph / Three.js)
当初はSigma.js(2D、WebGL)を採用していたが、SPEC v2.17で3d-force-graphへ切り替え、回転可能な3D球体状のレイアウトに刷新。描画データはSearchResponseのlevelsとpathのみから構築し、独自のBFSやAPI呼び出しは行わない。矢印キー/WASDによるパン、視点リセットにも対応。
7. 実ブラウザ・実WebGLでの検証
ラベルの重なりや3D描画の黒画面クラッシュなど、自動テストでは構造的に検出できないバグを、実際のChromeで1440×900・390×844の両ビューポートで目視確認して発見・修正。
8. Docker マルチステージビルド
Node.jsでフロントエンドをビルドした後、Node自体は破棄し、python:3.12-slim にビルド済み静的ファイルと3つのデータセットJSONだけをコピー。ベースイメージはタグではなくdigestで固定し、再現可能なビルドを保証。
9. リバースプロキシ配下でのHTTPS og:url
uvicorn標準のFORWARDED_ALLOW_IPSを利用し、信頼するプロキシのIP/CIDRを明示した場合のみX-Forwarded-Protoを信頼、og:urlのスキームを正しくHTTPSにする。デフォルトの挙動(未設定時はループバックのみ信頼)は変えない後方互換設計。
10. Windows対応のネットワークガード
バックエンドのテストスイートはソケットレベルで実ネットワークへのアクセスを遮断するガードを持つ。Windows固有のasyncio内部がループバックTCP通信を必要とする問題が発覚した際、ガード全体を緩めるのではなく「リテラルなループバックアドレスのみ許可(ホスト名解決はしない)」という最小限の修正で対応し、回帰テストを追加。
11. 自動化されたSPECトレーサビリティ
各テストが@pytest.mark.spec("BFS-04")や@spec FE-03のようなIDを持ち、SPEC.md内の対応表と照合される。必須IDにテストがない場合、または存在しないIDを参照するテストがある場合、テスト収集自体が失敗する仕組み。

K想定される質問と回答ポイント

Q.なぜ BFS を使ったのですか?
最短経路問題であり、エッジに重みがない(単純な「リンクがあるかないか」)ため、重み付きグラフ向けのダイクストラ法などは不要でした。BFSはenqueue時にゴール判定を行うことで、目的の人物が見つかった時点で打ち切れるため、実測でも約1万ノード規模でミリ秒単位で完了します。
Q.resolver と alias を分離した理由は?
「入力文字列をそのままグラフのキーにする」設計だと、英語・日本語・リダイレクトのゆらぎがグラフ全体の複雑さに波及します。resolverを独立させることで、グラフ自体は英語canonical nameだけを扱う単純な構造を保ち、多言語対応の複雑さをresolver層に閉じ込められます。
Q.なぜ DB を使わなかったのですか?
個人開発・学習目的のプロジェクトであり、運用コストをほぼゼロに保つことを明示的な制約としました。データセットは不変(immutable)で、起動時に一度だけメモリへロードすれば十分な規模(1万人未満)だったため、DBが持つ利点(永続化、同時書き込み制御など)がそもそも必要ありませんでした。
Q.なぜ runtime で Wikipedia API を呼ばない設計にしたのですか?
レート制限、レイテンシ、そして自分が制御できない外部サービスへの本番依存を避けるためです。エイリアス解決や画像URLなど「事前に計算できるもの」はすべてオフラインのFetcherに寄せ、ランタイムは純粋にメモリ上の参照だけで完結する設計にしました。トレードオフとして、名前解決のカバレッジはFetcherが取得した範囲に限定されます。
Q.Claude Code をどう使いましたか?
自分がSPECと実装方針を決めた上で、実際のコード変更・テスト実行・リポジトリ操作を指示して行わせるコーディングエージェントとして使いました。設計判断そのものはAIに委ねず、生成された実装は必ず自分でレビューしています。
Q.AI が間違えたときどう対応しましたか?
3Dグラフライブラリ(3d-force-graph)への切り替え時、コントロールの種類が既定の"trackball"のままだったため、キーボードパン機能を呼び出した瞬間に例外が発生し、画面が黒くなるバグが実ブラウザ検証で見つかりました。単体テストはWebGLをモックしているため検出できず、実ブラウザでの確認によって発見し、明示的に controlType: "orbit" を指定する修正を指示しました。
Q.実ブラウザ検証をなぜ行いましたか?
WebGL描画はテスト環境(jsdom)に存在しないため、自動テストでは構造的にモックせざるを得ません。ラベルの重なりや3D描画のクラッシュなど、モックされた層の「向こう側」で起きるバグは、実際にChromeを立ち上げて複数のビューポートサイズで目視確認しないと発見できませんでした。
Q.Docker / Vercel deployment で苦労した点は?
Vercelは通常の「なんでも動くコンテナホスティング」ではなく、Dockerfile.vercelという専用の命名規則でFluid Computeという独自の実行モデルにデプロイする仕組みでした。既存のDockerfileと重複させないため、Dockerfile.vercelをDockerfileへのgitシンボリックリンクとして構成し、アーキテクチャを変えずに両対応させました。またリバースプロキシ配下でのHTTPSスキーム反映は、FORWARDED_ALLOW_IPSを明示的に設定する必要がある、という一段特有の注意点があります。
Q.Six Degrees の「6」はこのアプリでどう扱っていますか?
アプリ内では「6」という数字自体をハードコードした制約や保証にはしていません。BFSは経路が存在する限り、何ステップであっても実際の最短経路を返します(0ステップ=同一人物から、データセット内に経路がなければfound: falseまで)。「6次の隔たり」はプロジェクトの発想の出発点であり、アプリの動作契約ではありません。
