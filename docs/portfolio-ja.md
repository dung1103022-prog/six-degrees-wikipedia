# 技術ポートフォリオ: Six Degrees of Wikipedia (Python)

**立場:** 個人開発です。要件定義、アーキテクチャ設計、実装仕様書(SPEC.md、全15版)の作成・改訂、そして技術的なトレードオフ判断とテストケースの設計は、すべて自分一人で行いました。実装そのものはAIコーディングエージェント(Claude Code)にコーディングを担当させ、私はその実装をレビュー・検証し、テストを実行したうえで受け入れる役割を担っています。ソースコードの一行一行を自分の手で書いたわけではありませんが、設計判断と品質保証には一貫して責任を持って取り組みました。

**技術スタック:** バックエンド Python 3.12 / FastAPI、フロントエンド React 19 / TypeScript / Sigma.js、Docker。
**現状:** 計画していた4フェーズをすべて実装完了。自動テスト383件(バックエンドpytest 280件、フロントエンドVitest 103件)が全てパスしています。本番用データセットも実際に生成・コミット済みで、直近のメンテナンス対応は `v1.0.1` として反映しています。

---

## 1. プロジェクト概要と目的

「Six Degrees of Wikipedia」は、Wikipedia上のリンクだけを辿って、ある人物Aから人物Bまで最短で何ステップで到達できるかを求めるアプリケーションです。着想元はGo実装の参考プロジェクト(`Rani-Codes/sixth_degree`)ですが、今回はPython/TypeScriptでゼロから設計し直しました。このプロジェクトで重視したのは、グラフ探索アルゴリズムそのものより、次の2点です。

1. **仕様駆動開発を一貫してやり切ること。** 実装判断が「なんとなく」で決まらない程度まで仕様を書き込み、レート制限ポリシーやライブラリの非推奨化、実際のブラウザでしか見えない描画バグといった「現実からの反証」が来るたびに、仕様書自体を正直に書き換え続けること。
2. **運用コストをほぼゼロに保つこと。** 個人・学習目的のプロジェクトであるとADRに明記したうえで、データベースもバックグラウンドジョブもスケジューラも持たず、コンテナ1つで完結する構成にしています。

加えて、英語入力でも日本語入力でも同じ人物にたどり着けることも必須要件としました。自分自身が使う前提のツールだからです。

## 2. 技術的な課題設定

出発点で衝突していた要件は主に3つあります。

- ユーザーは「Abe Shinzo」「安倍晋三」「安倍 晋三」のように気軽に入力しますが、グラフ自体は英語版Wikipediaのデータのまま保ちたい(でないと後続のアルゴリズムが全部複雑になる)。
- コストと複雑さの観点からデータベースやキャッシュサーバーは持たない(ADR-002/ADR-003)。同時に、レイテンシと「自分が制御できない外部サービスへの本番依存」を避けるため、リクエスト時にWikipediaを呼び出すことも禁止しました(ADR-009)。
- それでいて検索は「待たされている」という感覚を与えず、探索過程が見えるUIにしたい。

この3つの制約から、大きな決定を2つ下しました。1つ目は、事前計算はすべてオフラインで済ませ、実行時はメモリ上の解決だけを行うというデータ設計です。2つ目は、WebSocketではなく1回のHTTPレスポンスで結果を返すという通信方式です(詳細は後述)。

## 3. アーキテクチャ

全体は大きく4層に分かれます。ブラウザ上のReact SPAが `/api/*` と `/share` をFastAPIバックエンドに対して呼び出し、バックエンドはビルド済みSPA(`dist/`)自体の配信も兼ねます。バックエンド内部では、名前解決(Resolver)と最短経路探索(BFS)という2つの純粋関数モジュールが、起動時に一度だけメモリへロードされる読み取り専用のデータセット(`graph.json`・`people.json`・`aliases.json`)を参照します。このデータセットは、オフラインで手動実行するFetcherが `data/` 配下に書き出したJSONファイルを、Dockerビルド時にイメージへ`COPY`したものです。実行時にFetcherやMediaWiki APIが呼ばれることはありません。唯一の例外は、ブラウザが人物のサムネイル画像をWikimediaの画像CDNから直接取得する通信で、これが稼働中アプリケーションが行う唯一の外部通信です(ADR-009)。

コンポーネント単位のより詳細なアーキテクチャ図は `archify` という可視化ツールで別途作成しており(本リポジトリには含めていません)、必要に応じて提示可能です。

この構成を選んだ理由は、今振り返っても妥当だったと考えています。

- **ステートレス構成は運用作業そのものを丸ごと消してくれる。** データベースがなければマイグレーションもバックアップ戦略もコネクションプール調整も不要です。個人で立てて自分の財布で払うプロジェクトにとって、これは些細な利便性ではなく「放置しても大丈夫かどうか」を分ける差です。
- **1コンテナ・1デプロイ。** マルチステージのDockerfileでNodeを使ってフロントエンドをビルドし、そのNode自体は最終イメージに含めません。ランタイムイメージは `python:3.12-slim` とビルド済み静的ファイル、3つのJSONファイルだけです。デプロイ対象が1つ、落ちうる箇所も1つに絞られます。
- **「変な形で動き続ける」より「即座に落ちる」を選ぶ。** 起動時にデータセットやフロントエンドのビルド成果物が欠けている・不正な場合、プロセスは起動を拒否します。中途半端に「動いているように見えるが壊れている」コンテナより、`docker logs` で即座に気づけるクラッシュループの方がましだと考えました。

## 4. データパイプライン

`backend/fetcher.py`(約690行)は、このシステムの中でWikipediaと通信する唯一の場所であり、本番環境では一切実行されません。データセットを作り直したいときに、自分の手元で手動実行するツールです。

1. シード名リストを正式な英語版タイトルへ解決(リダイレクトやWikipedia独自のタイトル正規化を考慮)。
2. 出リンクを辿ってグラフを構築(`redirects=1` を付け、リダイレクト先へのリンクも正しくカウント)。
3. サムネイル・説明文・正規URL・日本語版への `langlinks` をバッチ取得(1件ずつではなく、1リクエストにつき最大50タイトルをまとめる)。
4. 英語版リダイレクト、続いて見つかった日本語タイトルそれぞれについて日本語版リダイレクトを取得し、由来(`en_redirect` / `ja_title` / `ja_redirect`)付きでエイリアスとして記録。
5. 3つの出力ファイルをまとめて検証し、すべて合格した場合のみ `data/` を置き換える。

実装で最も気を配ったのは正常系ではなく、失敗時の挙動です。

- **リクエスト間隔は「憶測」ではなく実際のポリシー確認から逆算しました。** WikimediaのRobotポリシーとレート制限に関するページを実際に読み、確認した日付と内容を仕様書にそのまま記録したうえで、両方の上限を余裕を持って下回る0.32秒という間隔を選びました。将来ポリシーが変わっても、仕様書の一行を直すだけで済みます。
- **HTTPステータスだけでなく、レスポンスの中身も必ず確認します。** MediaWiki APIはHTTP 200を返しつつ、JSON本文の中に `maxlag` エラーを含めてくることがあります。これを見落とすと「失敗したリクエストを成功扱いしてしまう」というバグになります。
- **リトライすべき失敗と、リトライしても無駄な失敗を明確に分けました。** 接続切断などのトランスポート層エラーはバックオフしながらリトライしますが、不正なリクエストやサポート外プロトコルはリトライしても直りません。`except Exception` で一律キャッチするのではなく、`httpx` の例外を種類ごとに列挙して仕分けています。
- **出力の置き換えはアトミックに行っています。** 3ファイルをまとめて検証・ステージングしてから、初めて本物の `data/` を一括で置き換えます。検証失敗や途中でのプロセス終了があっても、稼働中アプリが参照するデータセットが新旧混在の中途半端な状態になることはありません。

## 5. BFS探索と名前解決(リゾルバー)

どちらも外部依存のない小さなモジュールで、FastAPIもデータベースもI/Oも介さずに単体テストできる純粋関数として設計しています。

**BFS(`backend/app/graph.py`)** — アルゴリズム自体に特別な工夫はなく、`dict[str, list[str]]` の隣接リストに対する素直な幅優先探索です。目標判定はdequeue時ではなくenqueue時に行い、目標が見つかった瞬間に打ち切ります。探索順序の一貫性は、アルゴリズム側を複雑にするのではなく、データが事前にソートされているという前提に委ねました。あらゆる条件下で走査順序自体を制御しようとするより、そのほうが保守しやすい不変条件になると判断したからです。

**リゾルバー(`backend/app/resolver.py`)** は、実際に一番考え込んだ部分です。「辞書を引くだけ」では済まない、入力の衝突が起きるからです。

- 正式名称との完全一致は、他のどの判定よりも常に優先します。エイリアス側を見るのはそれで解決しなかった場合だけです。
- 正規化した入力が複数の正式名称、あるいは複数のエイリアス先に一致した場合は「曖昧(ambiguous)」として、ソート済みの候補を**すべて**返します。「辞書の走査順でたまたま先に出てきたものを返す」という実装は許容していません。同じ入力を複数回・異なるデータ構築順で流し、辞書の順序非決定性が結果に漏れ出さないことを確認するテストケースを設計しました。
- ある人物Xのエイリアスが、たまたま別の人物Yの正式名称と正規化後に一致した場合は、**Y側が勝ちます**。エイリアスが仮に単独で一意なターゲットを持っていたとしても、正式名称が常にエイリアスより優先されるというルールです。逆(エイリアス優先)にすると、非公式なリダイレクトが本来のページタイトルを静かに乗っ取れてしまうため、あえてこの優先順位にしました。

このプロジェクトで一番手こずった実バグも、ここにあります。Unicodeの正規化です。日本語の全角スペース、NFKCで等価になる文字(`²` と `2` など)、そして `_` と半角スペースの違い――これらは単純な文字列比較では、届いたUnicode形式によって結果がぶれてしまいます。そこで `match_key` という正規化ルールを一行の式として仕様書に固定し、実際に手動テスト中に自分がひっかかった入力を、そのままテストケースにしました。「`.lower()` に任せればいい」では済ませなかった部分です。

## 6. フロントエンドとグラフ描画

React 19 + TypeScript + Vite、グラフ描画は Sigma.js(WebGL)と Graphology を使い、`GET /api/search` が返すデータだけを描画しています。見た目を良くするためだけに新しいフィールドやエンドポイントを追加することは、意図的にしていません。そうしてしまうと、APIの契約が保証していないものを可視化側が勝手に表示することになるからです。

グラフの特徴:

- 見つかった経路全体を中心から1本の光線上に配置し、BFSの階層ごとに同心円を描くことで、「どこまで探索したか」と「どれが答えの経路か」を同時に一目で追えるようにしています。
- 実際には1回のHTTPレスポンスで結果を受け取っているにもかかわらず、階層を1段ずつタイマーで表示していくことで、探索が今まさに進んでいるような見せ方をしています。
- 探索されたが経路には含まれないノードは、起点からの距離に応じて色を薄くフェードさせ、密度がそのまま「深さ」として直感的に読めるようにしています。

Sigmaは意図的に自動テストの対象から外しています。WebGLはDOMテスト環境に存在しないためです。グラフを構築する純粋なデータ変換部分は直接単体テストし、Sigmaと繋ぐコンポーネントは「何を描くよう指示したか」を記録するフェイクSigmaクラスを用意し、それ相手にテストしています。それ以外のテストは `GraphView` 自体をモックで置き換えています。このトレードオフには実際に代償があり、それは10節で説明します。

## 7. テスト

| | ツール | 件数 |
|---|---|---|
| バックエンド | pytest | 280件 |
| フロントエンド | vitest + Testing Library | 103件 |
| **合計** | | **383件** |

数の多さより気に入っているのは、この383件すべてが名前付きの要件に紐づいていて、その紐付けが「運用ルール」ではなく「仕組み」で強制されている点です。各テストには `@pytest.mark.spec("BFS-04")` や `@spec FE-03` のようなIDが付いており、そのIDは `SPEC.md` 内の表に実在しなければなりません。テスト収集時にこの表を直接読み込み、必須IDにテストが存在しない場合や、存在しないIDを参照しているテストがある場合に、テスト実行自体を失敗させる仕組みを用意しました。コードのすぐ横にあるコメントが実装とズレていくのと同じように、仕様とテストが静かに乖離していくことを防ぐためです。

テストの設計で特に効果があったと感じている工夫が2つあります。1つは、実ネットワークへ出ようとする呼び出しを種類を問わず失敗させる、ソケットレベルのネットワークガードです。もう1つは、WebGLに依存するSigmaを意図的にモックで隔離したことで、裏を返せばモックの外側でしか見えないバグが残ってしまうと分かった点です。どちらも実際に問題を引き起こし、どう対応したかは10節で具体的に説明します。

## 8. Docker

1本のマルチステージ `Dockerfile` です。`node:24-slim` でフロントエンドをビルドし(`npm run build` は型チェックとバンドルを1コマンドで行います)、最終的な `python:3.12-slim` ランタイムイメージには `backend/app`、ビルド済み `dist/`、3つのデータセットJSONだけをコピーします。ランタイムイメージのPython依存関係は、ビルド時に `pyproject.toml` の依存リストからそのまま読み取っているため、Dockerfile側の記述が実際のピン留めからズレることが構造的にありません。`fetcher` や `test` 用の依存(httpx、pytestなど)はランタイムイメージには一切含まれません。データセットを変更する場合はイメージを作り直す前提で、ボリュームマウントや「データだけホットリロード」といった経路はあえて用意していません。

## 10. 直面した技術的課題と解決策

数ある中から、特に判断に迷った・後から効いてきたと感じる4件に絞って記載します。

- **計測せずに複雑さだけ増やしていたWebSocket。** 当初案ではBFSの進行状況をWebSocketでストリーミングする設計でした。実際に計測すると、約1万ノード規模のBFSはミリ秒単位で完了しており、WebSocketは純粋な過剰実装でした。1回のGETリクエストに置き換え、「探索を見ている感覚」はクライアント側のアニメーションタイマーに移しました。憶測ではなく計測に基づいてスコープを削った、自分として一番見てほしい判断です。
- **多言語入力とゼロ運用コストの両立。** 英語入力にも日本語入力にも対応させつつ、データベースも実行時のWikipedia呼び出しも持たないという制約がありました。名前のゆらぎを吸収する処理はすべてオフラインのFetcherに寄せ、実行時のリゾルバーは純粋なメモリ上の参照だけにすることで解決しています(仕組みの詳細は5節)。受け入れたトレードオフ――カバレッジはFetcherが見つけた範囲に限られ、実行時のライブフォールバックは持たない――は、仕様書に「却下した代替案」として明記しました。結果として、実行時の名前解決は追加のインフラを一切必要とせず動いています。
- **リリース後に判明した、Windows環境でのテスト基盤バグ。** バックエンドのテストは、モックし忘れた通信も含めてすべての実ネットワークアクセスを失敗させるソケットレベルのガードを備えています。ところが後日、Windowsの `asyncio` が内部で必要とするループバックTCP通信まで、このガードが遮断していたことが判明しました。それまでは、ドキュメント化されていないローカルのシムで表面上動いていただけでした。ガードを緩めるのではなく、「文字列としてのループバックアドレスのみ許可し(ホスト名解決はそれ自体が通信になるため行わない)、それ以外は従来通りすべて遮断する」形に絞り込み、実際にインストールされているガードそのものを直接検証する回帰テストを用意しました。結果として、外部ツールに頼らずWindows環境でもテストスイートがそのまま動くようになりました。
- **単体テストの設計そのものが見えなくしていたUIバグ。** Sigmaは設計上、自動テストからほぼ完全にモックで隔離しています。そのため、経路が長いときにラベル同士が重なる問題と、最後のノードのラベルがキャンバスの端で欠ける問題は、`vitest` を何度実行しても検出できませんでした。実際のChromeを使い、デスクトップ(1440×900)とモバイル(390×844)の2つの幅で本物のWebGL描画を目視確認して初めて気づき、ラベルを振り分ける段数を状況に応じて増減させるアルゴリズムに直して解決しました。修正の検証も、テストが通ることではなく、スクリーンショットとコンソールエラーの確認で行っています。

## 11. 成果

- 計画していた4フェーズ(データ/BFS/リゾルバー/API → `/share` → Fetcher → フロントエンド/Docker)を、実装中に見えてきた現実の制約(レート制限ポリシー、Unicodeの落とし穴、ライブラリの非推奨化、実ブラウザでしか見えない描画バグ)を反映しながら15回改訂した仕様書に沿って、すべて完了させました。改訂履歴は仕様書自体のchangelogに日付・理由付きで残しています。
- BFSは約1万ノード規模のグラフに対してミリ秒単位で完了することを設計初期に計測しており、この結果が「WebSocketをやめて1回のHTTPレスポンスで返す」という決定の裏付けになっています。
- 実際にアプリケーションを起動し、`/api/search`・`/api/people`・`/api/path`・`/share` の各エンドポイントがcurlで期待通りのレスポンスを返すこと、実際のChrome + 実WebGL環境でグラフが正しく描画されコンソールエラーが0件であることを、デスクトップ・モバイル双方の画面幅で確認しました。
- 起動時バリデーション(データセットとフロントエンドのビルド成果物の整合性チェック)はテストで裏付けられており、Dockerコンテナも同じ起動経路を使うため、データや成果物に欠損・不整合があれば即座に起動が失敗するfail-fast挙動になっています。
- 383件の自動テスト(バックエンド280件・フロントエンド103件)すべてが名前付き要件に紐づき、その対応関係が崩れたらビルド自体が失敗する仕組みで守られています。
- 自分が設計したFetcherが、実際に本番用データセット(9,997人・427,057エッジ・119,335エイリアス、曖昧マッチキー0件)を生成しました。

## 12. 残っている技術的負債

成果だけを並べず、未完了部分も正直に記載します。

- **未承認のエッジケースは、推測で実装するのではなく明示的に「未定」としています。** 空白のみの検索入力、255文字を超える入力、名前中のアンダースコアなどは、仕様書の中で「まだ決定していない事項」として記録され、対応する4つのテストID(`API-17`、`API-08`、`DAT-10`、`DAT-15`)は意図的に必須カバレッジから除外しています。
- **`anyio` を最新版より1つ前(4.14.2)に固定しています。** 依存先の `starlette` 1.6.0 がまだ新しいimportパスに追従していないために出る、`TestClient` 限定の非推奨警告を避けるための暫定対応です。`starlette` 側の対応を待って見直す予定です。
- **`SPEC.md` 自身の「残っている技術的負債」節が、まだ更新されていません。** 実際にはそこに記載されているN-1・N-2の2件はすでに後続のメンテナンスコミット(`8e88534`、`5e939f1`、タグ `v1.0.1`)で解決済みですが、仕様書のchangelogへの反映がまだできていません。
- **名前解決のカバレッジは、Fetcherが実際に取得した範囲に限られます。** 設計上、実行時にWikipediaへフォールバックする経路は存在しないため(ADR-013)、カバレッジを広げるにはコード変更ではなくデータの再取得が必要です。
- **検索履歴はブラウザ単位(`localStorage`)のみで、アカウントや複数端末間の同期はありません。** これは見落としではなく、「運用コストをほぼゼロに保つ」という制約(ADR-002/ADR-003)に基づいた意図的なスコープカットです。
